# 指示書06 Manus活用と代替（ふわで実行できる形）

目的: 教材でManusが担っている作業を棚卸しし、(a)Manusを使う場合の型と、(b)Manusなしで他のエージェント（Muse＝ふわ、Claude Code等）で代替する実行手順を定める。しばの指定により、標準は「ふわで代替できる構成」とする。

## Manusとは（教材での位置づけ）
指示を受けて計画・調査・実行・納品までを自律的に進めるエージェント型AI。強みはブラウザ操作を含む一連の作業の代行と、Skillsによる定型化、LINE等との連携による自動販売の運用。

## Manusを使う場合の型
- 依頼の型: 目的・対象・納品形式・制約を具体的に書き、大きな依頼は段階に分ける。
- 調査: 複数サイトの巡回、比較・検証、レポートや表への整理を任せる。
- ブラウザ操作: サイト閲覧、フォーム入力、データ抽出、比較調査。
- アプリ開発: アイデア→要件→画面設計→実装→公開を、プロンプトで仕様を固めながら反復修正する。
- LINE連携: 公式アカウントの設定と接続（Webhookやトークン等は現行仕様を確認）、自動返信・配信の実行役。
- 自動販売（オートマネタイズ）: リール生成などのSkills、SNS投稿、DM誘導、台本・投稿・反応のNotion一元管理。
- クレジット等の利用枠を把握し、大量利用時の節約（依頼の分割と再利用）を意識する。

## 代替対応表（Manusの役割 → ふわ等での代替）
| Manusの役割 | 代替手段 | 代替の可否と注意 |
|---|---|---|
| Web調査・競合リサーチ | ふわのブラウザ調査＋検索。表やレポート形式で納品 | 可。深さは依頼の設計次第 |
| ブラウザ操作（入力・抽出・比較） | ふわのブラウザ操作 | 可。ログインや承認が必要な操作は人の確認が入る |
| 楽天等の商品調査→投稿文→シート化 | ふわがブラウザ調査＋表作成まで一貫実行（指示書05の仕様） | 可。教材の丸投げプロンプトは「ふわへの依頼文」に読み替える |
| 資料・スライド・文書の作成 | ふわの成果物作成、またはClaude／Gamma等 | 可 |
| アプリ・サイトの作成と公開 | Claude Code＋GitHub→Vercel（指示書04） | 可 |
| 定期実行（毎朝の生成・収集） | ふわの予約タスク、またはZapier/Makeのフロー（指示書03） | 可。実行基盤が変わるだけ |
| LINE自動返信・配信の運用 | 公式LINEの自動応答設定＋Zapier/Makeフロー。文面生成はふわ | 部分的に可。常駐の自律運用はフロー側で設計する |
| SNS投稿の下書き量産 | ふわ＋型テンプレート（指示書02） | 可。投稿そのものは承認制 |
| Manus Skillsそのもの | ふわのスキル／Claude Skills（手順の定型化という考え方は共通） | 考え方は可。実装の互換性はない |
| Manusの画面・クレジット体系 | 代替なし | 対象外（作業レベルで代替する） |

## ふわへ依頼するときの型（Manus丸投げの読み替え）
Manus向けの「丸投げプロンプト」は、次の形に直してふわに渡すと同等の成果物が得られる。
1. 目的と成果物の形式（例: 表＋共有可能なファイル）
2. 対象と条件（ジャンル、評価や件数の下限、件数）
3. 収集項目の列定義
4. 文章の型（視点、長さ、構成、禁止表現）
5. 確認ポイント（人が承認してから先に進む箇所）
具体的な依頼文はプロンプト集のA1〜A3を使う。

## 代替できない・弱くなる点（正直な記録）
- Manusの常駐型の自律実行（人の画面を開いていない間の長時間タスク）は、代替側では予約タスクや外部フローの設計が必要で、即時の置き換えにはならない。
- ツール固有の連携機能は各サービスの現行仕様に依存する。代替可否は実装時に検証する。
- どのエージェントでも共通: ログイン、決済、公開などの重要操作は人の承認を挟む。
